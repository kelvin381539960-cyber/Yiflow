# Yiflow 项目计划 v1.0

## 1. 项目目标

Yiflow 的第一阶段目标不是马上写代码，而是建立一套可控、可验证、可持续推进的项目机制，确保后续能产出高质量方案和高质量产品。

本项目计划用于解决 4 个问题：

- 明确先做什么、后做什么。
- 明确每个阶段的输出物和验收标准。
- 明确 AI 可以做什么、不可以做什么。
- 明确如何避免 AI 导致的方案漂移、代码失控、需求膨胀和质量下降。

---

## 2. 项目原则

### 2.1 先计划，后执行

任何开发动作之前，必须先完成项目计划、需求边界、技术方案和验收标准。

不允许直接从一句自然语言需求进入代码实现。

### 2.2 先闭环，后扩展

第一阶段只追求跑通最小闭环：

> DSL → AST → Layout → Render → Validate

在这个闭环稳定之前，不做复杂编辑器、不做模板市场、不做云端协作。

### 2.3 AI 只能辅助，不能自动替代决策

AI 可以生成草案、拆任务、写代码、做评审，但不能自动决定：

- 产品边界
- 技术路线
- MVP 范围
- 架构关键取舍
- 是否进入下一阶段

这些必须由项目主控人确认。

### 2.4 每一步都要有可验证输出

每个阶段必须有明确产物，例如文档、Schema、示例 DSL、测试用例、可运行 CLI、渲染结果。

没有输出物，不算完成。

### 2.5 防止 AI 幻觉进入项目资产

所有 AI 生成内容必须经过检查，尤其是：

- 技术事实
- API 使用方式
- 第三方库能力
- Cursor / VS Code 扩展能力
- Layout 引擎能力
- 工程实现成本

不允许把未经验证的 AI 说法直接写成最终结论。

---

## 3. 项目阶段总览

项目分为 6 个阶段：

1. 项目治理与文档体系
2. 产品方案收敛
3. 技术方案验证
4. P0 技术样机
5. P1 内部可用版
6. P2 AI 工作流版

---

## 4. Phase 0：项目治理与文档体系

### 4.1 阶段目标

建立项目的工作方式、文档目录、任务机制和质量闸门。

这是为了防止项目被 AI 生成内容带散。

### 4.2 必做事项

- 建立 README。
- 建立项目目录结构。
- 建立 PRD 文档目录。
- 建立技术设计文档目录。
- 建立 examples 目录。
- 建立决策记录目录。
- 建立任务拆解文档。
- 建立 AI 使用规则。

### 4.3 输出物

```text
README.md
docs/prd/yiflow-prd-v1.3.md
docs/project-plan/yiflow-project-plan-v1.0.md
docs/adr/
docs/tech-design/
docs/ux/
docs/ai-rules/
examples/
```

### 4.4 验收标准

- 仓库打开后能看懂项目是什么。
- 文档目录结构清晰。
- 每个后续阶段都有明确入口。
- AI 不能绕过项目计划直接写核心代码。

---

## 5. Phase 1：产品方案收敛

### 5.1 阶段目标

把 Yiflow 从“想法和大方案”收敛为可开发、可验收的产品需求。

### 5.2 必做事项

- 明确 MVP 范围。
- 明确非目标。
- 明确核心用户路径。
- 明确首批支持的流程类型。
- 明确编辑能力边界。
- 明确成功标准。
- 明确 Cursor / Markdown 集成方式。
- 明确不做自由画布。

### 5.3 核心用户路径

MVP 只验证这一条主路径：

```text
用户写 DSL / AI 生成 DSL
        ↓
系统解析为 AST
        ↓
系统自动布局
        ↓
渲染为 SVG / HTML
        ↓
用户执行局部修改
        ↓
重新布局局部
        ↓
导出或嵌入文档
```

### 5.4 输出物

- PRD v1.4 或 v2.0。
- MVP 范围清单。
- 非目标清单。
- 用户任务流文档。
- 编辑能力清单。
- 成功标准清单。

### 5.5 验收标准

- 所有人能说清楚 MVP 做什么、不做什么。
- 不再把 Yiflow 定义成通用画图工具。
- 不再让 KYC 成为唯一场景，只作为样例之一。
- 每个功能都有明确验收方式。

---

## 6. Phase 2：技术方案验证

### 6.1 阶段目标

先验证技术路线是否成立，再进入正式开发。

### 6.2 必做事项

- 确认 DSL 格式。
- 确认 AST 数据模型。
- 确认 Parser 方案。
- 确认 Validator 规则。
- 确认 Layout 引擎选型。
- 确认 Render 输出方式。
- 确认 CLI 结构。
- 确认 Cursor 集成路线。

### 6.3 关键技术问题

必须验证以下问题：

1. YAML DSL 是否足够表达审批泳道图。
2. AST 是否能支持局部 patch。
3. Layout 引擎能否稳定处理泳道、主路径、异常路径、回跳路径。
4. SVG 渲染是否足够用于 PRD 和文档。
5. CLI 能否在本地稳定 render / validate。
6. Cursor 是否适合采用 Markdown Preview + Webview Editor 的双层模式。

### 6.4 输出物

- 技术设计稿 v1.0。
- DSL Schema v0.1。
- AST Model v0.1。
- Layout 选型说明。
- Render 方案说明。
- CLI 方案说明。
- Cursor 扩展方案。

### 6.5 验收标准

- 技术路线不依赖未经验证的假设。
- 所有关键库能力都经过最小验证。
- 能说清楚为什么选该方案，以及替代方案是什么。

---

## 7. Phase 3：P0 技术样机

### 7.1 阶段目标

做出第一个能跑的最小技术闭环。

P0 不追求好看，不追求完整编辑器，只验证底层链路成立。

### 7.2 P0 范围

必须支持：

- 读取 `.swimflow.yaml`。
- 解析 DSL。
- 转换为 AST。
- 做基础校验。
- 做基础自动布局。
- 输出 SVG。
- 提供 CLI 命令。

### 7.3 P0 不做

- 不做可视化编辑器。
- 不做 Cursor 插件。
- 不做 AI 修改。
- 不做复杂模板。
- 不做自由拖拽。

### 7.4 输出物

```text
packages/core
packages/layout
packages/renderer
packages/cli
examples/approval-flow.swimflow.yaml
examples/kyc-flow.swimflow.yaml
```

### 7.5 验收标准

能执行：

```bash
yiflow validate examples/approval-flow.swimflow.yaml
yiflow render examples/approval-flow.swimflow.yaml -o output.svg
```

并得到：

- 校验结果。
- SVG 文件。
- 可读的泳道流程图。

---

## 8. Phase 4：P1 内部可用版

### 8.1 阶段目标

让 Yiflow 可以用于真实工作中的简单流程图。

### 8.2 P1 范围

必须支持：

- Markdown 代码块预览。
- 本地 HTML Preview。
- 基础节点编辑。
- 改职责归属。
- 局部整理。
- 锁定主路径。
- SVG / PNG 导出。
- 错误提示和定位。

### 8.3 P1 不做

- 不做完整自由编辑器。
- 不做多人协作。
- 不做云端流程资产库。
- 不做复杂权限。

### 8.4 输出物

- Yiflow Editor 轻量版。
- Markdown Preview 能力。
- 示例流程图集合。
- 内部试用说明。
- 已知问题清单。

### 8.5 验收标准

用户能在 15 分钟内完成：

1. 打开示例流程图。
2. 看懂结构。
3. 修改一个节点文案。
4. 插入一个步骤。
5. 把一个节点移动到另一个泳道。
6. 导出 SVG。
7. 放入 PRD 或文档。

---

## 9. Phase 5：P2 AI 工作流版

### 9.1 阶段目标

让 AI 真正参与流程图生成和修改，但保持可控。

### 9.2 P2 范围

必须支持：

- 自然语言生成初始 DSL。
- 自然语言转 Operation。
- 局部上下文选择。
- patch 预览。
- patch 校验。
- 影响范围提示。
- 修改失败时降级为建议。

### 9.3 AI 修改原则

AI 修改必须遵循：

1. 默认不重写整图。
2. 默认输出 operation。
3. 默认只影响局部。
4. 应用前必须 validate。
5. 修改后必须展示影响范围。
6. 不确定时必须降级为建议，而不是强行修改。

### 9.4 输出物

- AI Operation Prompt。
- Context Slicing 规则。
- Patch 校验流程。
- AI 修改测试集。
- 失败案例库。

### 9.5 验收标准

AI 能完成以下修改，并保持主路径稳定：

- 加一步。
- 删除一步。
- 改职责归属。
- 添加补件分支。
- 整理异常支路。
- 锁定主路径后局部修改。

## 10. AI 风险控制机制

### 10.1 主要风险

AI 可能导致的问题包括：

- 需求范围膨胀。
- 方案表述看起来正确但不可实现。
- 技术选型幻觉。
- 代码一次性生成太多，难以维护。
- 修改时破坏已有结构。
- 文档和代码不一致。
- 忽略边界条件。
- 过早引入复杂能力。

### 10.2 控制原则

必须建立以下控制机制：

#### 机制 1：AI 输出必须可审查

AI 不能只输出最终结果，必须输出：

- 修改内容。
- 修改原因。
- 影响范围。
- 不确定点。
- 验证方式。

#### 机制 2：小步提交

AI 生成代码必须小步提交。

每次只允许完成一个明确任务，例如：

- 新增 DSL schema。
- 新增 parser。
- 新增一个 validator。
- 新增一个示例。
- 新增一个 CLI 命令。

禁止一次性生成整个系统。

#### 机制 3：先测试后扩展

每个核心模块必须先有测试样例，再扩展复杂能力。

#### 机制 4：文档和代码同步

任何能力变更都必须同步更新：

- PRD 或技术设计。
- 示例文件。
- 测试用例。
- README 或使用说明。

#### 机制 5：关键决策必须写 ADR

以下变更必须写 ADR：

- DSL 格式变化。
- AST 结构变化。
- Layout 引擎切换。
- Cursor 集成方式变化。
- 是否支持自由拖拽。
- 是否支持新的导出格式。

## 11. 质量闸门

### 11.1 进入开发前

必须完成：

- PRD 审查。
- 技术方案审查。
- MVP 范围确认。
- 核心数据模型确认。
- 示例流程确认。

### 11.2 每个模块完成前

必须满足：

- 有输入输出说明。
- 有测试样例。
- 有错误处理。
- 有 README 或注释说明。
- 有最小可运行验证。

### 11.3 每次 AI 生成代码后

必须检查：

- 是否偏离需求。
- 是否引入不必要复杂度。
- 是否破坏已有接口。
- 是否有测试。
- 是否能本地运行。
- 是否更新文档。

### 11.4 进入下一阶段前

必须完成阶段复盘：

- 本阶段完成了什么。
- 哪些假设被验证。
- 哪些问题仍未解决。
- 是否需要调整路线图。
- 下一阶段是否值得开始。

### 12.1 第一批任务：项目治理

- 创建 README。
- 创建项目计划。

- 创建 ADR 模板。

- 创建 examples 目录。

- 更新 PRD 到 v1.4。
- 单独输出 MVP Scope。
- 单独输出 User Flow。
- 单独输出 UX Interaction Spec。
- 单独输出 Success Metrics。

### 12.3 第三批任务：技术设计

- 输出 DSL Schema。
- 输出 AST Model。
- 输出 Operation Protocol。
- 输出 Validator Design。
- 输出 Layout Design。
- 输出 Renderer Design。
- 输出 CLI Design。

- 初始化工程结构。
- 实现 DSL parser。
- 实现 AST model。
- 实现 validator。
- 实现基础 layout。
- 实现 SVG renderer。
- 实现 CLI。
- 增加示例和测试。

## 14. 第一阶段建议执行顺序

当前最合理的执行顺序是：

1. 补 README。
2. 补 AI 使用规则。
3. 补 ADR 模板。
4. 补 examples 示例。
5. 补 DSL Schema v0.1。
6. 补 AST Model v0.1。
7. 补技术设计稿 v1.0。
8. 再进入 P0 代码实现。

不要先写代码。

---

## 15. 最终结论

Yiflow 要做成高质量项目，第一步不是开发，而是建立项目主控机制。

本项目计划要求：

- 先计划。
- 再收敛。
- 再验证。
- 再开发。
- 每一步都要有文档、示例、测试和质量闸门。

AI 在项目中是生产力工具，不是项目主控者。

只有把 AI 约束在明确的任务、上下文、验收标准和质量闸门里，Yiflow 才能避免变成“AI 生成的一堆看似完整但不可维护的东西”。
