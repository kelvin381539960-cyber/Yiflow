# Yiflow PRD v1.3

## 版本定位

本版是在 v1.2 基础上的模块化与工作化优化版本。

核心调整方向：

- 从“一个流程图工具”升级为“AI 时代的结构化流程表达与编辑系统”。
- 从“单图生成”升级为“可在真实工作中持续维护、复用、协作、验证的流程资产”。
- 从“功能堆叠”升级为“模块化能力架构”，便于后续拆分开发、测试、迭代和商业化。
- 从“AI 出图”升级为“AI 生成 + 人工轻改 + 规则校验 + 版本沉淀”的稳定工作流。

# 1. 产品概述

## 1.1 产品名称

**Yiflow**

## 1.2 命名结构

- 产品名：Yiflow
- 技术内核：SwimFlow Engine
- DSL 名称：SwimFlow DSL
- 编辑器：Yiflow Editor
- Cursor 扩展：Yiflow for Cursor

对外统一叫 **Yiflow**。内部保留 SwimFlow Engine / SwimFlow DSL 作为技术模块名，避免品牌和技术概念混乱。

## 1.3 一句话定义

Yiflow 是一个面向 AI 协作的结构化流程图工具，支持通过自然语言生成流程图，并通过受控编辑、自动布局、规则校验和文档集成，让业务流程图可以在真实工作中稳定使用和持续维护。

## 1.4 产品定位

Yiflow 不是通用画图工具，也不是传统 BPMN 平台。

Yiflow 的定位是：

> **AI-native 流程资产编辑系统**

它的核心价值不是“画得更自由”，而是：

- AI 能生成
- 人能轻改
- 结构可维护
- 图能进文档
- 流程可复用
- 修改可追踪
- token 成本可控

# 2. 背景与问题

## 2.1 当前工作中的真实痛点

在产品、研发、运营、风控、合规、项目管理等工作中，流程图经常用于：

- 梳理业务规则
- 说明系统流转
- 对齐职责边界
- 评审需求方案
- 沟通异常处理
- 沉淀 SOP 和流程资产

但现有工具存在明显断层。

## 2.2 Mermaid 类工具的问题

Mermaid 适合快速写图，但在真实工作中有几个问题：

- 泳道表达弱，职能归属不稳定。
- 复杂流程排版容易乱。
- 用户无法直接轻量调整图面。
- 修改时经常需要整段重写。
- AI 反复调图会消耗大量 token。
- 图一旦复杂，就难以长期维护。

## 2.3 draw.io 类工具的问题

draw.io 适合手动画图，但不适合 AI 工作流：

- 初始绘制成本高。
- 不适合自然语言生成。
- 结构语义不够标准化。
- 难以进行局部 patch。
- 后续修改依赖人工拖拽。
- 不适合作为可计算的流程资产。

## 2.4 传统 BPMN 工具的问题

BPMN 工具标准强，但对普通产品和业务用户偏重：

- 学习成本高。
- 表达过于专业。
- 不适合日常 PRD 和业务评审。
- AI 生成和轻量编辑体验弱。
- 与 Cursor / Markdown / 文档工作流结合不自然。

## 2.5 核心机会

AI 时代的流程图，不应只是图片，而应该是：

> **可生成、可编辑、可校验、可复用、可沉淀的结构化流程资产**

Yiflow 要填补的是 Mermaid、draw.io、BPMN 之间的空白：

- 比 Mermaid 更稳定。
- 比 draw.io 更 AI-native。
- 比 BPMN 更轻。
- 比普通图片更可维护。
- 比纯文本流程更适合沟通。

# 3. 产品目标

## 3.1 核心目标

### G1. AI 可生成真实业务流程图

用户用自然语言描述业务流程，Yiflow 能生成具备泳道、节点、分支、异常、回跳的结构化流程图。

### G2. 流程图可持续维护

生成后的图不是一次性图片，而是可通过 DSL / AST / Operation 持续维护的结构化资产。

### G3. 用户可轻量编辑

用户无需理解底层 DSL，也能完成常见修改：

- 加一步
- 删一步
- 改文案
- 改职责归属
- 调整顺序
- 添加分支
- 局部整理

### G4. 布局稳定且可控

系统默认自动布局，但支持受控微调、局部整理和锁定，避免“AI 一改就全乱”。

### G5. Token 成本可控

修改默认使用局部 patch 和局部上下文，不反复重传整图。

### G6. 适合真实工作环境

支持 Markdown / Cursor / 文档导出 / 版本沉淀 / 校验提示，适合产品经理和研发在日常工作中使用。

# 4. 非目标

## 4.1 不做自由画布

不做 Figma / draw.io 式无限自由画布，不支持任意位置摆放、任意手画线。

## 4.2 不做完整 BPMN 替代

不覆盖完整 BPMN 标准，不做复杂事件模型、完整执行引擎、工作流自动化。

## 4.3 不做多人实时协同平台

MVP 不做多人实时在线编辑、评论、权限系统。

## 4.4 不以 Mermaid 兼容为主卖点

可以导出 Mermaid 结构，但不承诺布局保真。

## 4.5 不做流程执行系统

Yiflow 只表达流程，不执行流程，不做审批流后端引擎。

# 7. 产品原则

## P1. 结构优先

图首先是业务结构，其次才是视觉表现。

## P2. 自动布局优先

布局由引擎负责，不让 AI 或用户反复描述“线短一点、别交叉”。

## P3. 受控编辑

允许用户改，但只允许合法、结构安全的修改。

## P4. 局部优先

用户修改默认影响局部，不默认重排全图。

## P5. AI 友好

DSL、Operation、上下文策略必须适合 AI 生成和修改。

## P6. 工作流友好

必须适配 Markdown、Cursor、文档导出和日常评审。

## P7. 可验证

流程图要有 schema 校验、结构校验、错误提示，不能只靠“看起来像”。

# 8. 模块化产品架构

Yiflow 按模块拆分为 9 个核心模块。

---

## 8.1 Authoring Module：流程生成模块

负责将自然语言、模板、DSL 转换为初始流程图。

能力：

- 自然语言生成流程图
- 选择流程模板
- 生成 SwimFlow DSL
- 生成 Graph AST
- 首图质量检查

输入：

- 自然语言
- 模板
- 已有 DSL
- 已有 AST

输出：

- 可渲染流程图
- 可编辑 AST
- 可保存 DSL

---

## 8.2 Graph Core Module：图模型模块

负责维护唯一真相。

能力：

- Graph AST 管理
- 节点、泳道、边、路径类型管理
- 结构合法性校验
- AST 与 DSL 双向转换
- Operation 应用

核心原则：

> Graph AST 是唯一真相，DSL 是表达层，SVG/HTML 是渲染结果。

---

## 8.3 Layout Module：布局引擎模块

负责稳定排版。

能力：

- 自动布局
- 泳道布局
- 主路径识别
- 异常路径弱化
- 回跳路径处理
- 局部重排
- 锁定对象避让
- visual override 合并

布局目标：

- 主路径清晰
- 分支可读
- 回跳不乱
- 职责归属明确
- 局部修改不影响全图

---

## 8.4 Editor Module：受控编辑模块

负责用户可视化编辑。

能力：

- 节点编辑
- 边编辑
- 分支编辑
- 改职责归属
- 合法拖拽
- 局部整理
- 锁定
- 撤销 / 重做

编辑原则：

> 不是自由画布，而是结构安全的流程编辑器。

---

## 8.5 AI Operation Module：AI 修改模块

负责把用户自然语言修改转为 operation。

能力：

- NL → Operation
- 局部上下文选择
- patch 生成
- patch 校验
- patch 应用
- patch 后预览
- 错误回退

典型输入：

- “在人工审核后加一步主管复核”
- “把开户移到系统泳道”
- “整理补件分支，但别动主流程”

典型输出：

```json
{
  "action": "insert_node_after",
  "target_node_id": "manual_review",
  "new_node": {
    "id": "supervisor_review",
    "type": "process",
    "text": "主管复核",
    "lane": "risk"
  }
}
```

# 9. 核心数据模型

## 9.1 唯一真相

Yiflow 内部以 Graph AST 作为唯一真相。

```text
自然语言 / DSL / 编辑器操作
        ↓
Graph AST
        ↓
Layout Model
        ↓
Render Result
```

## 9.2 核心实体

- Diagram
- Lane
- Node
- Edge
- Path
- Branch
- Group
- Constraint
- Layout
- Override
- Operation

## 9.3 基础 DSL 示例

```yaml
diagram:
  id: sample_approval_flow
  title: 示例审批流程
  direction: LR

lanes:
  - id: applicant
    title: 申请人
  - id: system
    title: 系统
  - id: reviewer
    title: 审核人

nodes:
  - id: submit
    type: process
    text: 提交申请
    lane: applicant

  - id: validate
    type: process
    text: 系统校验
    lane: system

  - id: review
    type: process
    text: 人工审核
    lane: reviewer

edges:
  - id: e1
    from: submit
    to: validate
    path_type: main

  - id: e2
    from: validate
    to: review
    path_type: main
```

# 10. Operation 机制

## 10.1 设计原则

Yiflow 不应频繁重写整张图，而应优先用 operation 修改 AST。

## 10.2 Operation 类型

### 节点类

- insert_node
- insert_node_after
- insert_node_between
- delete_node
- rename_node
- change_node_type
- move_node_to_lane

### 边类

- add_edge
- delete_edge
- relabel_edge
- reroute_edge

### 分支类

- add_branch
- delete_branch
- reorder_branch
- set_branch_type

### 布局类

- local_relayout
- relayout_branch
- relayout_lane
- full_relayout
- set_visual_override

### 锁定类

- lock_node
- lock_branch
- lock_main_path
- unlock

## 10.3 Operation 示例

```json
{
  "action": "move_node_to_lane",
  "node_id": "open_account",
  "target_lane": "system",
  "relayout_scope": "local"
}
```

# 11. 用户语言映射

## 11.1 新增

| 用户说 | 系统动作 |
|---|---|
| 加一步 | insert_node_after |
| 中间插一步 | insert_node_between |
| 多一个分支 | add_branch |

## 11.2 修改

| 用户说 | 系统动作 |
|---|---|
| 改个名字 | rename_node |
| 这个不是风控做的 | move_node_to_lane |
| 这两个换一下 | reorder_node |

## 11.3 整理

| 用户说 | 系统动作 |
|---|---|
| 整理一下 | local_relayout |
| 只整理这条支线 | relayout_branch |
| 不要动主流程 | lock_main_path + relayout_branch |

## 11.4 降级策略

当用户表达不清时，默认遵循：

1. 局部修改
2. 局部整理
3. 当前泳道整理
4. 全图重排

默认不直接全图重排。

# 12. 布局规则

## 12.1 主路径优先

主路径应保持连续、清晰、尽量水平推进。

## 12.2 异常路径弱化

异常、驳回、补件、失败路径不与主路径争抢中心位置。

## 12.3 回跳路径分层

回跳路径使用独立通道展示，避免穿越主路径。

## 12.4 Decision 展开规则

通过类路径优先作为主分支，拒绝、补件、异常作为侧支。

## 12.5 局部重排规则

局部重排只影响指定节点、分支或泳道。锁定对象不参与重排。

## 12.6 Override 清理规则

当 override 过多导致图不稳定时，应提供：

- 清除当前节点微调
- 清除当前分支微调
- 清除全图微调
- 保留语义重新布局

包含：

- 保存
- 撤销
- 重做
- 整理选区
- 整理本分支
- 全图重排
- 导出

## 13.5 合法拖拽

允许：

禁止：

- 任意坐标摆放
- 任意手画线
- 拖出流程结构边界

# 14. Cursor / Markdown 集成

## 14.1 集成模式

Yiflow 采用：

> **Markdown-first + Editor-on-demand**

## 14.2 Markdown 预览

用户在 `.md` 中写：

```md
```swimflow
...
```
```

预览中直接渲染图。

## 14.3 点击进入编辑

预览图右上角提供：

- Open in Yiflow Editor
- Edit Diagram

点击后进入专属编辑器。

## 14.4 编辑后回写

## 14.5 专用文件模式

支持 `.swimflow.yaml` 文件作为独立流程图资产。

# 15. 校验机制

## 15.1 语法校验

检查 DSL 是否可解析。

## 15.2 结构校验

检查：

- 节点 id 唯一
- edge 引用存在
- lane 存在
- decision 至少两条出边
- 不存在孤立主节点

## 15.3 业务结构校验

检查：

- 主路径是否完整
- 是否存在未处理异常支路
- 回跳路径是否可读
- 是否存在多个无法解释的终点

## 15.4 用户提示

错误提示必须能定位到行或节点，并给出修复建议。

# 16. Token 策略

## 16.1 Token 成本来源

- 首图生成
- 单次修改
- 连续多轮修改
- 大图上下文
- 错误修复

## 16.2 策略

- 首图可以传全量需求。
- 修改默认传局部子图。
- 大图只传目标节点上下游。
- AI 输出 operation，不输出整图。
- operation 应用前先校验。

## 16.3 工作中可感知目标

用户应感觉：

- 改图快
- 不乱改
- 不反复解释
- 大图也能改局部
- 多轮修改后仍稳定

# 18. 工作化能力设计

为确保 Yiflow 适合真实工作场景，需要补充以下工作化能力。

## 18.1 版本信息

每个图应记录：

- diagram id
- title
- author
- created_at
- updated_at
- version
- change_summary

## 18.2 变更摘要

每次保存时生成简短变更摘要，例如：

- 新增“主管复核”节点
- 将“开户”移动到系统泳道
- 整理补件分支
- 锁定主路径

## 18.3 导出前检查

导出前检查：

- 是否有校验错误
- 是否存在未连接节点
- 是否有未命名分支
- 是否有布局冲突
- 是否包含过多 override

## 18.4 文档嵌入友好

导出图应适合：

- PRD
- Markdown
- 飞书
- Notion
- Confluence
- GitHub README

# 19. 成功标准

## 19.1 产品能力成功标准

- 能生成真实业务流程泳道图，而不是只支持单一 KYC 场景。
- 能覆盖审批流程、职责泳道图、系统与人工混合流程、异常和回跳流程。
- 支持至少 5 类高频修改：插入、删除、重排、改职责、改文本、局部整理。
- 输出可直接用于文档，不需要二次排版。
- 用户可以不依赖 AI 完成至少 3 类轻量编辑。
- 大图修改可以只影响局部。

## 19.2 UX 成功标准

- 首图可以直接用于讨论。
- 主路径明显且正确。
- 节点泳道归属基本合理。
- 回跳路径可读。
- 小改不会意外改变主路径。
- 局部整理后用户不觉得失控。
- 连续 5 次修改后结构仍稳定。

## 19.3 AI 成功标准

- AI 能从自然语言生成初始图。
- AI 能把修改请求转成 operation。
- AI 默认不重写整图。
- AI 能解释本次改动影响范围。
- AI 修改失败时能降级为建议操作。

# 20. 路线图

## P0：技术样机

目标：证明结构闭环成立。

包含：

- DSL
- AST
- Parser
- Validator
- 基础布局
- 静态渲染
- render CLI

## P1：内部试用版

目标：用于真实工作中的简单流程图。

包含：

- Markdown 预览
- Yiflow Editor
- 节点编辑
- 改职责归属
- 局部整理
- 锁定主路径
- SVG / PNG 导出

## P2：AI 工作流版

目标：让 AI 真正参与流程图生成和修改。

包含：

- NL → Operation
- 局部上下文策略
- AI 修改预览
- 影响范围提示
- 连续修改稳定性优化

## P3：团队工作版

目标：适合团队内沉淀流程资产。

包含：

- 版本信息
- 变更摘要
- 模板库
- 流程资产目录
- 文档平台嵌入增强

# 21. 风险与应对

## 21.1 首图质量不稳定

应对：

- 使用模板增强
- 增加首图质量校验
- 通过典型场景训练提示词和规则

## 21.2 用户觉得不够自由

应对：

- 强化合法拖拽
- 增加局部整理
- 增加锁定和影响范围提示

## 21.3 复杂图仍然乱

应对：

- 强化主路径和异常路径规则
- 增加折叠分支
- 提供分层视图

## 21.4 Token 节省不明显

应对：

- 强制 operation-first
- 大图采用局部上下文
- 建立 token 基线测试

## 21.5 产品过度工程化

应对：

- MVP 聚焦“出图 + 小改 + 导出”
- 不过早做模板市场、云端协作、复杂权限

# 22. 最终定义

Yiflow 的最终产品定义是：

> **一个面向 AI 时代的结构化流程资产工具。**

它不是简单画图，而是把业务流程变成可生成、可编辑、可验证、可维护、可复用的工作资产。

核心链路是：

> **自然语言描述 → AI 出图 → 人工轻改 → 规则校验 → 局部整理 → 文档沉淀**

只要这条链路稳定，Yiflow 就不是一个“画图小工具”，而是能真正进入工作流的 AI 产品力工具。
